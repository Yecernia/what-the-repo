# 用户自带的模型 API Key

**简体中文** · [English](provider-keys.md)

这里说明 what-the-repo 如何保存和使用用户自己提供的模型 API Key，以及部署者需要做什么来保护它们。报告问题请看[安全报告说明](../SECURITY.zh-CN.md)。

## 保存

在 PostgreSQL 部署中，用户的 Key 以 AES-256-GCM 认证加密的密文保存，并绑定到对应的用户和连接。服务端的加密密钥由部署密钥材料派生，与数据库和源码仓库分开保存。已有的密文继续使用原来的部署密钥读取；没有迁移方案时，不要更换它。

仅供开发使用的 FileStore 使用加密的内存密钥库，进程重启后不会保留。

## 使用

Key 只在需要时解密。启动和设置页的可用性检查不会加载明文 Key，密钥库也不缓存明文。浏览器不会把 Key 保存在 Cookie 或浏览器存储中，设置接口只返回是否可用和固定的星号。更换 Key 需要先验证新 Key；删除会移除保存的密文，但不会中止已经开始的上游请求，也不会在厂商那边吊销这个 Key。

管理凭据的请求要求 HTTPS（本机开发除外），新 Key 通过 `x-wtr-byok-draft` 请求头传入。普通聊天请求不会重复发送已保存的 Key。应用诊断只记录受控的错误类别，不记录上游错误原文。已知的 Key 回显会在写入 Agent 事件和会话记录前过滤掉，但无法保证识别恶意上游对它做的任意变换。

## 部署者的责任

- 不要让代理、APM 或调试日志收集凭据请求头、Authorization、Cookie、请求正文或完整的运行时对象。
- 加密密钥不得进入 Git、数据库导出或容器镜像。
- HTTPS 保护的是传输过程，不是数据库内容；字段加密也保护不了已经被攻破的应用进程。内存转储、交换文件和历史备份需要另行管控；清除 JavaScript 引用并不等于安全擦除内存。

建议用户使用专用、限额的 Key，一旦怀疑泄露，就到厂商那边吊销。
