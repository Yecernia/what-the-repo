# 首批能力矩阵

状态：源码观察加已有产物验证，2026-08-10。表中的“当前结论”不是最终排名；同目标的成对产物尚未补齐。

| 产品所需能力 | CodeBoarding | Understand Anything | 当前判断与待验证项 |
| --- | --- | --- | --- |
| 文件清单与覆盖 | 指纹和 `file_coverage.json` 记录全部纳入/排除文件 | `scan-project.mjs` 确定性枚举并分类代码、配置、文档和基础设施文件 | 两者都能提供确定性清单；需统一忽略规则后比较 |
| 符号和位置 | LSP 产出类、函数、定义、引用和位置，`methods_index` 暴露到正式结果 | Tree-sitter 结构提取后生成类/函数节点和 `lineRange` | 小样本先比较符号召回和行号有效性 |
| 文件导入 | 静态分析内部拥有依赖事实，但 `analysis.json` 不直接提供完整导入图 | import map 由 Tree-sitter 与语言解析器确定性生成，最终为 `imports` 边 | UA 的正式图谱更直接；CB 可能需要新适配层读取安全静态格式 |
| 函数调用 | LSP 调用图是组件划分和 `all_edges` 的主要事实来源 | 同文件结构来自脚本，跨文件 `calls` 由 Worker 结合导入和符号判断 | 已在 `python-edge-cases` 上建立 58 条高置信调用真值：CodeBoarding 暴露 14 条，命中 14 条（精确率 1.0、召回率 0.2414）；UA 暴露 43 条，命中 38 条（精确率 0.8837、召回率 0.6552）。闭包返回另记为 `returns`，不混入调用边。两者输出粒度不同，不能只比较边数。 |
| 继承与实现 | 静态分析结果包含继承关系，但正式输出暴露程度有限 | 图谱支持 `inherits`、`implements`，由 Worker依据结构结果生成 | 需要在多继承和跨文件继承样本上比较 |
| 架构组件 | 程序先聚类调用图，再由 LLM 分组、命名、校验和修复 | `architecture-analyzer` 根据图拓扑和目录语义生成命名架构层 | 组件与层不是同一概念，不能只比较数量 |
| 组件关系 | API surface、静态调用证据和 LLM 关系说明结合，并补充静态关系 | 图谱边直接用于层和导览，边类型覆盖代码与非代码对象 | 需比较证据覆盖、重复边和不可验证说明 |
| 非代码文件 | 主要围绕代码、依赖、文档和项目元数据，正式架构偏代码组件 | 明确建模 config、document、service、pipeline、schema、resource 等对象 | UA 当前覆盖面更广，但语义边可靠性需抽样核对 |
| 代码证据引用 | `key_entities`、`file_methods`、调用位置和源码引用进入正式结果 | 节点带 `filePath`、可选 `lineRange`，层和导览引用节点 ID | 两者都可作为证据来源；需统一来源、commit 和置信字段 |
| 主动学习路线 | 没有面向学习者的长期教学状态，输出以架构结果为主 | 生成固定 `tour`，但不会持续判断用户掌握情况 | 都不能直接满足主动教师，需要自己的教学 Agent |
| 并行与多 Agent | Python 调度多个分析任务；Agent 类共享 LangChain 运行骨架 | 宿主 Skill 最多并行启动多个 `file-analyzer` Worker | UA 的多 Agent 依赖宿主，不是可直接迁移的运行时 |
| 结构校验 | Pydantic、修复器、验证器、重试和最佳结果选择较完整 | 合并脚本、引用完整性检查、Reviewer 和严格 JSON 合同 | 应比较错误被发现和被静默修复的比例 |
| 增量更新 | 指纹、变化集、簇变化、组件 ID 和递归更新较深入 | 文件指纹、Git 变化文件和已有图谱增量更新 | 需在同一修改序列上比较结果稳定性与成本 |
| 可观测性 | 已有模型、工具、Token 和运行统计模块 | Skill 有阶段进度和警告，缺少统一的通用 Trace 运行时 | 产品必须自行定义统一 Trace 契约 |
| 不可信仓库安全 | 已发现 pickle、缓存写入目标仓库、遥测和语言服务边界问题 | 读取仓库并运行自身解析脚本，仓库文本仍是不可信输入 | 两者都不能未经加固直接成为线上安全边界 |

## 结论边界

- 当前只确认两套项目“拥有哪些机制”和“现有产物是否结构完整”。
- 事实召回、错误率、价值点质量、成本和增量稳定性必须通过同目标的成对运行决定。
- 产品自己的证据图谱需要同时保留事实来源和 LLM 参与程度，不能只保存一条没有出处的边。

## 首个成对样本结果

`python-edge-cases` 的干净事实层基线已经形成：CodeBoarding 的源码符号召回为 63/63，Understand Anything 为 38/63；UA 命中 15 个重点符号中的 14 个，但漏掉嵌套类 `UserProfile.Address`。两者都覆盖 10 个文件，UA 图谱保留全部 13 条内部导入，并生成 4 个架构层和 7 步导览；CodeBoarding 的架构结果表示 7 个文件，同时提供 5 个组件、4 条组件关系和完整方法索引。

当前倾向不是“选一个 JSON”：完整符号事实和高置信关系更接近 CodeBoarding，面向浏览的文件层和导览更接近 UA。产品证据图谱的类型契约见 `server/src/domain/snapshot.ts`：保留完整事实层，再按教学任务派生简化视图，而不是在提取阶段永久丢弃被判定为“不显著”的符号。
